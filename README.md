# Mini NPU 시뮬레이터

MAC(Multiply-Accumulate) 연산으로 입력 패턴이 **Cross(십자가)**와 **X** 중 어느 필터에 더 가까운지 판별하는 Python 콘솔 애플리케이션입니다.
외부 라이브러리 없이 표준 라이브러리만 사용합니다. Python 3.8 이상에서 실행됩니다.

## 실행 방법

```bash
python main.py                                   # 대화형 메뉴 (1 / 2 / 0)
python main.py --mode 1                          # 3×3 직접 입력
python main.py --mode 2 --data data.json         # JSON 일괄 판정 + 성능 분석 + 리포트
python main.py --mode 2 --data data_edge.json    # 예외 케이스 데모
python main.py --mode 2 --repeat 50              # 성능 측정 반복 횟수 변경 (기본 10)
```

| 파일 | 설명 |
|---|---|
| `main.py` | 시뮬레이터 전체 (데이터 구조, MAC, 모드 1/2, 성능 분석, 리포트) |
| `data.json` | 5×5 / 13×13 / 25×25 필터와 패턴 12건 (정상 데이터, 전부 PASS) |
| `data_edge.json` | 라벨·스키마·크기·부동소수점 문제를 일부러 넣은 데이터 (실패 원인 분석용) |

## 구성

### 데이터 구조: `Grid`
- n×n 2차원 배열을 저장하며, `get(r, c)`와 `set(r, c, v)`로 특정 위치의 값을 읽고 씁니다.
- `Grid.from_rows()`는 정사각형 여부, 행/열 수, 숫자 타입을 검증합니다(`bool`은 거부). 크기 제한이 없어서 3×3, 5×5, 13×13, 25×25 모두 처리합니다.

### MAC 연산: `mac(pattern, filter)`
```python
total = 0.0
for r in range(n):
    for c in range(n):
        total += pattern.get(r, c) * filter.get(r, c)
```
NumPy 없이 이중 반복문으로 구현했고 float 점수를 반환합니다. 두 배열의 크기가 다르면 `ValueError`를 발생시킵니다.

### 모드 1: 3×3 입력
- 필터 A, 필터 B, 패턴을 한 줄씩(공백 구분) 입력받습니다.
- 한 줄의 값 개수가 틀렸거나 숫자로 읽을 수 없으면 `입력 형식 오류: 각 줄에 3개의 숫자를 공백으로 구분해 입력하세요.`를 출력하고, 해당 행렬을 처음부터 다시 입력받습니다.
- 출력 항목은 A/B 점수, 연산 시간(ms), 판정(A / B / 판정 불가)입니다.

### 모드 2: data.json
처리 순서는 필터 로드, 패턴별 판정, 성능 분석, 결과 리포트입니다.

예상하는 스키마:
```json
{
  "filters":  { "size_5": { "cross": [[...]], "x": [[...]] }, "size_13": {...}, "size_25": {...} },
  "patterns": { "size_5_1": { "input": [[...]], "expected": "+" }, ... }
}
```
- 패턴 키 `size_{N}_{idx}`에서 정규식으로 N을 뽑아 `size_N` 필터를 고릅니다.
- 다음 문제는 **그 케이스만 FAIL로 처리하고 원인을 남깁니다**. 프로그램은 종료되지 않습니다.
  - 키 형식 오류, 필드(`input`/`expected`) 누락, 해당 크기 필터 없음
  - 크기 불일치, 비정사각 배열, 숫자가 아닌 값
- 필터가 잘못된 경우에는 그 필터만 건너뛰고 경고를 출력합니다.

### 라벨 정규화
내부에서는 표준 라벨 `Cross`와 `X` 두 가지만 사용합니다. 입력값은 `strip()`과 `lower()`를 거친 뒤 매핑합니다.

| 원본 | 출처 | 표준 라벨 |
|---|---|---|
| `+`, `cross` | expected / 필터 키 | `Cross` |
| `x` | expected / 필터 키 | `X` |
| 그 외 | — | 인식 불가 → FAIL |

정규화가 필요한 이유는 같은 개념이 데이터 안에서 `+`, `cross`, `Cross `처럼 여러 형태로 적혀 있기 때문입니다. 원본 문자열을 그대로 비교하면 `"+" != "Cross"`가 되어 **로직은 맞는데 FAIL이 나는** 오류가 생깁니다. 입력 단계에서 한 번 정규화해 두면 이후의 비교와 출력은 모두 같은 기준으로 이루어집니다.

### 점수 비교 정책 (epsilon)
```python
if abs(score_a - score_b) < 1e-9:  # 동점 → UNDECIDED / 판정 불가
```
부동소수점은 이진수로 정확히 표현되지 않습니다. 예를 들어 `0.1 + 0.2`는 `0.30000000000000004`이므로, 수학적으로는 같은 두 점수도 `>` 비교에서 한쪽이 이긴 것처럼 나올 수 있습니다. 허용오차 이내의 차이는 동점으로 간주해서 판정이 우연한 오차에 좌우되지 않도록 했습니다.

## 리포트

### 1. 실행 결과 요약

| 데이터 | 전체 | 통과 | 실패 |
|---|---|---|---|
| `data.json` | 12 | 12 | 0 |
| `data_edge.json` | 11 | 2 | 9 |

### 2. 실패 원인 분석 (`data_edge.json`)

원인은 세 가지로 분류했습니다. **데이터/스키마 문제**, **로직 문제**, **수치 비교 문제**입니다.

| 케이스 | 증상 | 분류 | 원인과 대응 |
|---|---|---|---|
| `size_5_1` (expected `" Cross"`), 필터 키 `"Cross "` | PASS | 라벨/스키마 | 대소문자와 공백이 섞인 라벨입니다. 정규화가 없었다면 FAIL이나 KeyError가 났을 케이스로, `strip().lower()` 매핑으로 해결했습니다. |
| `size_5_2` (expected `"X"`) | PASS | 라벨/스키마 | 대문자 X입니다. 정규화로 처리했습니다. |
| `size_5_5` (expected `"o"`) | FAIL | 데이터 | 정의되지 않은 라벨입니다. 데이터를 수정해야 하며, 프로그램은 원인을 남기고 다음 케이스로 넘어갑니다. |
| `pattern_9` | FAIL | 스키마 | 키가 `size_{N}_{idx}` 규칙을 따르지 않아 N을 뽑을 수 없습니다. |
| `size_7_1`, `size_25_1` | FAIL | 스키마 | 해당 크기의 필터가 `filters`에 없습니다. |
| `size_13_1` | FAIL | 데이터 | 키는 N=13인데 입력은 12×12입니다. 이대로 MAC을 돌리면 IndexError가 나거나 일부만 계산되므로 사전에 크기를 검증합니다. |
| `size_5_6` | FAIL | 데이터 | 배열에 숫자가 아닌 `'a'`가 들어 있습니다. |
| `size_5_7` | FAIL | 데이터 | 2×3 배열로, 정사각형이 아닙니다. |
| `size_5_3` | FAIL (UNDECIDED) | **수치 비교** | Cross 점수는 `0.1+0.2 = 0.30000000000000004`, X 점수는 `0.3`입니다. 단순 `>`로 비교하면 Cross가 이긴 것으로 나오지만, 실제 차이는 오차 수준이라 epsilon 정책에 따라 동점(UNDECIDED)으로 처리했습니다. |
| `size_5_4` (모든 칸이 1) | FAIL (UNDECIDED) | 데이터(라벨) | 두 필터의 1의 개수가 같아서 점수가 9:9로 실제 동점입니다. 판정 로직은 정상이고, Cross로 라벨링한 데이터 쪽이 잘못되었습니다. |

`data.json`에서는 **로직 문제가 원인인 실패가 0건**입니다. 진단은 아래 순서로 진행했습니다.

1. 점수가 `-`인지(MAC 전에 중단되었는지) 확인합니다. `-`이면 데이터/스키마 문제입니다.
2. 점수가 있고 두 점수가 거의 같으면 수치 비교 문제(UNDECIDED)를 의심합니다.
3. 점수 차이가 분명한데도 판정이 expected와 다르면, 필터나 MAC 로직, 또는 expected 라벨 자체를 의심합니다.

### 3. 시간 복잡도 분석

필터 1개에 대한 MAC은 N×N 칸마다 곱셈 1회와 덧셈 1회를 수행하므로 **O(N²)**입니다. 필터 2개와 비교하는 판정 1건은 2·N²회이고, 상수배이므로 그대로 O(N²)입니다. 패턴 P개를 일괄 처리하면 O(P·N²)입니다.

측정 결과 (워밍업 1회 후 10회 반복 평균, 실행 환경에 따라 절댓값은 달라질 수 있음):

| 크기 | 연산 횟수 N² | 평균(ms) | 평균/N²(µs) |
|---|---|---|---|
| 3×3 | 9 | 0.00079 | 0.088 |
| 5×5 | 25 | 0.00173 | 0.069 |
| 13×13 | 169 | 0.00956 | 0.057 |
| 25×25 | 625 | 0.03677 | 0.059 |

- 13×13 → 25×25 구간에서 N²는 3.7배, 시간은 3.8배 늘었습니다. **곱셈 1회당 시간(평균/N²)이 약 0.06µs로 일정**하므로 실행 시간이 N²에 비례한다는 것을 확인할 수 있습니다.
- 3×3에서 25×25로 가면 N²는 69배인데 시간은 약 46배만 늘었습니다. 크기가 작을수록 함수 호출이나 `range` 생성 같은 고정 오버헤드의 비중이 커서 칸당 시간이 높게 나오기 때문입니다. N이 커지면 이 오버헤드는 무시할 수 있는 수준이 됩니다.
- 측정 방법: `time.perf_counter()`를 사용했고, 첫 호출에서 생기는 캐시나 인터프리터 효과를 빼기 위해 워밍업을 1회 먼저 실행했습니다. 그다음 반복 측정해 평균과 최소값을 함께 출력합니다. 1회만 측정하면 OS 스케줄링 노이즈 때문에 값이 크게 흔들립니다.

**NPU와의 연결**: CPU에서 순차 반복문으로 계산하면 N²회를 하나씩 처리합니다. N²개의 곱셈은 서로 독립적이므로, NPU는 MAC 유닛 수천 개로 이 곱셈들을 동시에 처리하고 덧셈은 트리 구조로 누적합니다. 이렇게 하면 실제 소요 시간(지연)을 크게 줄일 수 있습니다. 전체 연산량은 O(N²) 그대로이고, 줄어드는 것은 연산을 처리하는 데 걸리는 시간입니다.
